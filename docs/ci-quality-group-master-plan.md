## 1. Visión del ecosistema

Dos proyectos independientes que se construyen **en secuencia** y se conectan por un **contrato mínimo**:

```
   ┌──────────────────────────────┐         ┌──────────────────────────────┐
   │  SITIO WEB (Astro)           │         │  CHATBOT (Next.js)           │
   │  <dominio> · Cloudflare      │         │  panel.<dominio> · Vercel    │
   │  • Gráfico, sin login        │         │  • Webhook Meta (3 canales)  │
   │  • CTA → WhatsApp ───────────┼────────►│  • Motor RAG + memoria       │
   │  • [futuro] widget web ──────┼────────►│  • /api/chat/web (canal web) │
   └──────────────────────────────┘         │  • Panel admin               │
                                            └──────────────────────────────┘
                                                          ▲
                                                   Messenger · WhatsApp · Instagram
```

**Principio rector:** el bot es el **cerebro y se construye primero**; la web es la **cara y se construye después**; la integración del chat web es la **última milla, opcional**, y ya queda cableada en ambos.

## 1.5 Organización del repositorio (MONOREPO)

**Decisión:** ambos proyectos viven en **un solo repositorio** (más accesible y mejor para el agente).
**Repo:** `https://github.com/tridentcol/ci-quality-group-web-agent.git` (creado y vacío).

### Estructura
```
ci-quality-group-web-agent/
├── apps/
│   ├── chatbot/              # Next.js  → panel.<dominio> (Vercel). Usa el chatbot-blueprint
│   └── website/              # Astro    → <dominio> (Cloudflare Pages). Usa el website-blueprint
├── packages/
│   └── shared/               # @cqg/shared: tipos del contrato /api/chat/web + tokens de marca
├── docs/                     # los 5 documentos (.md): blueprints, master-plan, prompts, README
├── pnpm-workspace.yaml
├── package.json              # scripts raíz (pnpm --filter ...)
├── CLAUDE.md                 # raíz: mapa del monorepo (abajo)
└── README.md
```

### Configuración de workspace
`pnpm-workspace.yaml`:
```yaml
packages:
  - apps/*
  - packages/*
```
`package.json` (raíz) scripts útiles:
```json
{
  "scripts": {
    "dev:bot": "pnpm --filter chatbot dev",
    "dev:web": "pnpm --filter website dev",
    "build:bot": "pnpm --filter chatbot build",
    "build:web": "pnpm --filter website build"
  }
}
```

### `packages/shared` (la pieza que mantiene todo sincronizado)
Exporta una sola fuente de verdad para lo que ambos comparten:
```ts
// packages/shared/src/chat-contract.ts
export interface ChatRequest  { sessionId: string; message: string }
export interface ChatResponse { reply: string; handoff?: boolean; quickReplies?: string[] }
// packages/shared/src/brand.ts → tokens de color compartidos
```
Ambas apps lo consumen con `"@cqg/shared": "workspace:*"`. Así el contrato de integración (Fase C) es **type-safe de extremo a extremo** y la marca no se desincroniza.

### Deploys independientes (mismo repo, distinto destino)
- **Vercel (chatbot):** Project Settings → **Root Directory = `apps/chatbot`**. Vercel detecta Next.js y construye solo esa app.
- **Cloudflare Pages (website):** Build command `pnpm install && pnpm --filter website build`, **Build output `apps/website/dist`**, root = raíz del repo.
- Cada push despliega ambos a su destino; ninguno pisa al otro.

### `CLAUDE.md` raíz (mapa del monorepo — crear en la raíz del repo)
```markdown
# CI Quality Group — Monorepo

Dos apps + un paquete compartido. pnpm workspaces.

## Estructura
- apps/chatbot   → Next.js, panel.<dominio> (Vercel). Guía: docs/ci-quality-group-chatbot-blueprint.md
- apps/website   → Astro, <dominio> (Cloudflare Pages). Guía: docs/ci-quality-group-website-blueprint.md
- packages/shared (@cqg/shared) → tipos del contrato /api/chat/web + tokens de marca
- docs/          → blueprints, plan maestro, prompts, README

## Reglas del monorepo
1. Trabaja SIEMPRE dentro de una app a la vez (apps/chatbot O apps/website). No mezcles cambios.
2. Cada app tiene su propio CLAUDE.md con sus reglas; respétalo al entrar.
3. Tipos/marca compartidos → packages/shared. No los dupliques en cada app.
4. Comandos con filtro: `pnpm --filter chatbot ...` / `pnpm --filter website ...`.
5. Cada app despliega por separado (Vercel / Cloudflare). No acoples sus configs.
```

> **Para el agente:** un `CLAUDE.md` por nivel (raíz + por app) mantiene el contexto acotado; trabajar con `--filter` y por app evita cargar la otra app sin necesidad (ahorro de tokens).

## 2. Orden de construcción global

> Regla de oro: **no empieces una fase sin cerrar los criterios de salida de la anterior.** Cada fase entrega algo funcional por sí mismo.

### FASE 0 — Prerrequisitos (en paralelo a todo, empieza YA)
Lo más lento del proyecto. Arráncalo el día 1.
- [ ] **Meta Business** verificado (Business Verification).
- [ ] Página de Facebook + Instagram Profesional vinculado + **WhatsApp Business Account** con número dedicado.
- [ ] **Meta App** con productos Messenger, Instagram, WhatsApp y **App Review** de permisos por canal (ver Anexo 17 del blueprint del chatbot).
- [ ] Cuentas: Neon, OpenAI, Clerk, Vercel (+Blob), Inngest, Cloudflare (dominio ya comprado).
- **Salida:** tienes tokens/IDs de los 3 canales y todas las API keys.

### FASE A — CHATBOT (el cerebro) · *se construye primero*
Sigue **íntegro** el `ci-quality-group-chatbot-blueprint.md`, Steps 1–16. Incorpora además el **sistema de memoria** de §3 de este documento (addendum al modelo de datos).
- **Por qué primero:** la web depende de que exista el número de WhatsApp activo y, en el futuro, del endpoint `/api/chat/web`. El valor de negocio (atención al cliente) vive aquí.
- **Criterios de salida (gate A→B):**
  - [ ] El bot responde correctamente en **los 3 canales** con RAG estricto.
  - [ ] Panel operativo: subir conocimiento, editar precios, ver leads/huecos/conversaciones.
  - [ ] **Memoria** funcionando (corto plazo + perfil de cliente — §3).
  - [ ] **Handoff humano** funcionando (echo → pausa + aviso WhatsApp — §4).
  - [ ] Desplegado en `panel.<dominio>` y estable.
  - [ ] **El número de WhatsApp del bot está activo** → es el dato que necesita la web.

### FASE B — SITIO WEB (la cara) · *se construye después*
Sigue **íntegro** el `ci-quality-group-website-blueprint.md`, Steps 1–12.
- **Por qué después:** necesita el número de WhatsApp activo (Fase A) para el CTA, y deja cableada —apagada— la integración web-chat.
- **Criterios de salida (gate B→C):**
  - [ ] Landing desplegada en el **dominio raíz** (Cloudflare Pages).
  - [ ] CTA de WhatsApp abre el deep link y **cae en el bot** (probado en móvil real).
  - [ ] `ChatWidget` presente pero **apagado** (`PUBLIC_ENABLE_WEB_CHAT=false`), sin coste.
  - [ ] Lighthouse > 90, SEO local en su sitio.

### FASE C — Activación del chat web (la última milla) · *opcional, cuando se quiera*
Enciende el widget web usando el mismo cerebro. **No tiene prisa.** Pasos en §5.
- **Criterios de salida:**
  - [ ] Ruta `/api/chat/web` viva en el chatbot (canal `web`), con CORS para el dominio raíz.
  - [ ] `PUBLIC_ENABLE_WEB_CHAT=true` en la web → widget conversa con el bot.
  - [ ] La conversación web alimenta la **misma memoria** (perfil de cliente, leads, huecos).

```
FASE 0 ───────────────────────────────────────────────►  (continua)
        FASE A (chatbot) ──► gate ──► FASE B (web) ──► gate ──► FASE C (integración)
```

## 3. Sistema de memoria

El bot debe sentirse humano, y eso exige **recordar**. Tres capas, de corto a largo plazo. **Las capas 1 y 3 ya están en el blueprint del chatbot; la capa 2 (perfil de cliente) y los resúmenes son un addendum a incorporar en la Fase A.**

### Capa 1 — Memoria conversacional (corto plazo) ✅ ya en el blueprint
- Tabla `messages`: cada turno carga el historial reciente de la conversación.
- **Ventana**: últimos N mensajes (p. ej. 12) o desde el último resumen, para no exceder tokens.

### Capa 2 — Memoria del cliente (largo plazo) 🆕 addendum a la Fase A
Que el bot recuerde al cliente **entre conversaciones distintas** (otro día, otro mensaje).

**Nueva tabla `customer_profiles`:**
| Field | Type | Notes |
|-------|------|-------|
| id | uuid | PK |
| channel | text | Canal de origen |
| external_id | text | ID del usuario en ese canal |
| contact | text | Teléfono/email (clave de unificación entre canales) |
| name | text | Nombre conocido |
| company | text | Empresa, si aplica |
| facts | jsonb | Hechos aprendidos: materiales de interés, volúmenes típicos, preferencias, idioma/tono |
| last_seen_at | timestamptz | |
| created_at | timestamptz | |
| UNIQUE | (channel, external_id) | |

**Cómo funciona:**
- Al iniciar/continuar una conversación, se busca el `customer_profiles` por `(channel, external_id)` y se **inyecta un resumen del perfil en el system prompt** ("Cliente recurrente: interesado en cobre, suele comprar al por mayor").
- Tras cada conversación relevante, el bot (o un job Inngest) **actualiza `facts`** con lo nuevo aprendido.
- **Unificación entre canales** (opcional): si en dos canales aparece el mismo `contact` (capturado vía lead), se enlazan los perfiles → memoria continua aunque el cliente cambie de red social.

### Capa 3 — Memoria de conocimiento (RAG) ✅ ya en el blueprint
- `knowledge_chunks` (lo que la empresa sabe) + el **bucle de huecos**: pregunta sin respuesta → el admin la resuelve → se inyecta a la base. La organización "aprende" con el tiempo.

### Resúmenes de conversación 🆕 addendum
- Campo `conversations.summary` (text). Cuando una conversación supera X mensajes, un job Inngest **resume** lo anterior y el bot usa `resumen + últimos mensajes` → conversaciones largas sin perder contexto ni disparar coste.

> **Privacidad (Ley 1581/2012):** la memoria de cliente se rige por `retention_months` y el aviso de tratamiento de datos. Permitir borrado de perfil bajo solicitud.

## 4. Sistema de handoff (bot → humano)

Ciclo de vida completo del relevo. **Ya está en el blueprint del chatbot; aquí queda consolidado de punta a punta.**

| Etapa | Qué ocurre |
|-------|-----------|
| **1. Disparo** | El cliente pide hablar con una persona, **o** el bot no encuentra respuesta (RAG vacío) y `log_knowledge_gap`, **o** la negociación supera `max_auto_discount_pct`. → `request_human_handoff(reason)`. |
| **2. Aviso** | `notify()` envía un **mensaje de WhatsApp al admin** (`ADMIN_WHATSAPP_NUMBER`) con canal, cliente y motivo. (Requiere plantilla aprobada de WhatsApp Cloud API.) |
| **3. Pausa del bot** | `conversation.status = human_controlled`. El bot **deja de responder** ese hilo. |
| **4. Detección automática de toma de control** | Si el humano responde desde la **bandeja de Meta**, llega un evento *echo* → el sistema marca `human_controlled` aunque no se haya pulsado nada. El bot nunca pisa al humano. |
| **5. Atención humana** | El equipo conversa desde Meta; los mensajes se guardan (`role = human_agent`) y **alimentan la memoria** del cliente. |
| **6. Devolución al bot** | Desde el panel (`/conversations`), el admin pulsa **"liberar control"** → `status = bot_active`. El bot retoma con todo el contexto e historial intactos. |

**Continuidad de handoff entre canales (futuro):** con la memoria de cliente por `contact`, si alguien empieza en la web (canal `web`) y sigue por WhatsApp, el bot lo reconoce y no le hace repetir nada.

## 5. Contrato e integración web ↔ bot (Fase C)

Un único contrato, ya cableado en ambos proyectos. Activarlo es trivial.

### El contrato (ya documentado en §8 del blueprint web)
```
POST https://panel.<dominio>/api/chat/web
Body:  { sessionId: string, message: string }
Resp:  { reply: string, handoff?: boolean, quickReplies?: string[] }
```

### Pasos de activación (cuando se decida)
**En el chatbot (Next.js):**
1. Crear `app/api/chat/web/route.ts`: valida con Zod → `upsert` de `conversations` con `channel='web'`, `external_id = sessionId` → corre el pipeline `generate()` **existente** (mismo RAG, mismas tools, misma memoria) → responde `{ reply, handoff, quickReplies }`.
2. Habilitar **CORS** para `https://<dominio>`.
3. (Opcional) Rate limiting por `sessionId`/IP.
> No requiere tocar el modelo de datos ni el motor: el canal `web` ya encaja (`conversations.channel` es texto libre, la memoria es agnóstica al canal).

**En la web (Astro):**
4. Poner `PUBLIC_ENABLE_WEB_CHAT=true` y `PUBLIC_CHATBOT_API_URL=https://panel.<dominio>/api/chat/web`.
5. El `ChatWidget` (ya creado, apagado) se hidrata y empieza a conversar.

**Resultado:** la web pasa de "solo redirige a WhatsApp" a "atiende también en el sitio", **con el mismo cerebro, memoria y handoff**. Sin refactor.

| Canal del bot | Texto libre: `messenger` \| `whatsapp` \| `instagram` \| `web` |

## 7. Handoff de desarrollo (cómo construir con Claude Code)

Todo ocurre en **un solo monorepo** (§1.5). Orden:

0. **Inicializar el monorepo (una vez):**
   - Clona `https://github.com/tridentcol/ci-quality-group-web-agent.git`.
   - Crea `pnpm-workspace.yaml`, `package.json` raíz, `CLAUDE.md` raíz (§1.5) y la carpeta `docs/` con los 5 documentos.
1. **App 1 (chatbot) → `apps/chatbot`:**
   - Pide a Claude Code: *"Construye la app en `apps/chatbot` siguiendo `docs/ci-quality-group-chatbot-blueprint.md`, incluido el sistema de memoria. Crea su CLAUDE.md propio."*
   - **No avances** hasta cumplir el **gate A→B** (§2).
2. **App 2 (web) → `apps/website`:**
   - *"Construye la app en `apps/website` siguiendo `docs/ci-quality-group-website-blueprint.md`. Deja la integración del chat cableada pero apagada (§8). Usa `@cqg/shared` para los tipos del contrato."*
   - Cumple el **gate B→C**.
3. **Integración (Fase C), cuando se quiera:**
   - En `apps/chatbot`: *"Añade la ruta `/api/chat/web` según el plan maestro §5, tipada con `@cqg/shared`."* Luego enciende el flag en `apps/website`.

> Tres niveles de `CLAUDE.md`: raíz (mapa del monorepo) + uno por app (de cada blueprint). El agente trabaja **una app a la vez** con `pnpm --filter`.

## 9. Resumen ejecutivo

- **Se construye el bot primero** (el cerebro y el valor de negocio), **luego la web** (la cara que lo alimenta), **y al final —si se quiere— el chat web** (la última milla, ya cableada).

- **La integración** entre web y bot es un único contrato (`/api/chat/web`, canal `web`), ya preparado en ambos: encenderlo no exige refactor.
- Todo respeta **Habeas Data (Colombia)**, español, COP, y una marca coherente entre los dos dominios.
