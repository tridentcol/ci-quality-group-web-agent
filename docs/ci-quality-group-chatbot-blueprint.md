# CI Quality Group — Chatbot — Blueprint

> Generated by The Architect on 2026-06-03
> Archetype: API / Backend Service (motor conversacional con IA + RAG, multicanal Meta, con panel de administración)

---

## 1. Project Overview

### Vision
**CI Quality Group Chatbot** es un asistente de atención al cliente impulsado por IA que responde de forma natural y profesional a través de los tres canales de Meta —**Messenger** (principal), **WhatsApp** e **Instagram**— desde un único cerebro. Se alimenta del conocimiento real de la empresa (catálogos, especificaciones técnicas, ubicaciones, indicaciones, precios) mediante RAG (Retrieval-Augmented Generation), de modo que **solo responde con información verificada y nunca inventa**.

CI Quality Group ofrece servicios de **disposición final de desechos, chatarrización y compra/venta de chatarra**. El bot resuelve dudas de clientes 24/7, maneja **precios minoristas y mayoristas**, **captura solicitudes/leads** para cotización, y deriva a un humano cuando hace falta. Todo se gestiona desde un **panel de administración propio** aislado en `panel.<dominio>`, separado del sitio de presentación de la empresa que vive en el dominio raíz.

### Goals
- Responder cualquier duda del cliente con tono **natural, neutral, formal, profesional y directo** (español de Colombia), sin sonar a bot enlatado.
- Dar al administrador **control total**: subir conocimiento (PDF/Word/PPT/texto/links), editar precios en COP, aprobar descuentos, ver conversaciones y métricas.
- Capturar leads y notificar al administrador **por WhatsApp** en tiempo real.
- Mejorar solo: registrar preguntas sin respuesta y permitir resolverlas en el panel para enriquecer la base de conocimiento.
- Coste operativo bajo (~$10–30/mes) con un único proveedor de IA (OpenAI).

### Success Metrics
- % de conversaciones resueltas por el bot sin relevo humano.
- Nº de leads capturados / mes y tasa de conversión a cotización.
- Nº de "huecos de conocimiento" detectados y resueltos (la base mejora con el tiempo).
- Tiempo medio de primera respuesta (objetivo: < 5 s).
- Coste de API por conversación (objetivo: < $0,01).

## 2. Tech Stack

| Layer | Technology | Why |
|-------|-----------|-----|
| Framework | **Next.js 16** (App Router) | Panel de administración + webhooks de Meta + API interna en **un solo proyecto y un solo deploy**. Menos piezas, menos coste de mantenimiento. |
| Language | **TypeScript** (strict) | Tipado de extremo a extremo; seguro y mantenible. |

| Database | **PostgreSQL + pgvector** (Neon) | Una sola BD guarda config, conversaciones **y** los embeddings vectoriales. A volumen bajo-medio no se necesita BD vectorial aparte → menos coste y complejidad. |

| DNS | **Cloudflare** | Dominio ya comprado; gestiona el subdominio `panel.<dominio>`. |
| Channels | **Meta Graph API** (Messenger, Instagram Messaging, WhatsApp Cloud API) | Webhook unificado para los tres canales. |
| Package Manager | **pnpm** | Rápido y eficiente en disco. |

### Relationships
- `knowledge_sources` 1—N `knowledge_chunks` (al borrar la fuente se borran sus chunks).
- `conversations` 1—N `messages`, 1—N `leads`, 1—N `knowledge_gaps`.
- `customer_profiles` 1—N `conversations` (un cliente puede tener varias conversaciones en el tiempo → memoria de largo plazo).
- `materials` 1—N `leads` (opcional).
- `bot_config` es singleton (fila id=1), creada por el seed.
- Resolver un `knowledge_gap` crea una nueva `knowledge_source` tipo `faq` → genera un `knowledge_chunk` embebido.

### Database Schema (Drizzle — extracto clave)
```typescript
import { pgTable, uuid, text, timestamp, numeric, boolean, integer, jsonb, vector, index, unique } from 'drizzle-orm/pg-core'

export const knowledgeSources = pgTable('knowledge_sources', {
  id: uuid('id').defaultRandom().primaryKey(),
  type: text('type').notNull(),                       // pdf|docx|pptx|txt|link|faq
  name: text('name').notNull(),
  originalUrl: text('original_url'),
  status: text('status').notNull().default('pending'),
  error: text('error'),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow(),
})

export const knowledgeChunks = pgTable('knowledge_chunks', {
  id: uuid('id').defaultRandom().primaryKey(),
  sourceId: uuid('source_id').notNull().references(() => knowledgeSources.id, { onDelete: 'cascade' }),
  content: text('content').notNull(),
  embedding: vector('embedding', { dimensions: 1536 }).notNull(),
  metadata: jsonb('metadata'),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow(),
}, (t) => ({
  embeddingIdx: index('chunks_embedding_idx').using('hnsw', t.embedding.op('vector_cosine_ops')),
}))

export const materials = pgTable('materials', {
  id: uuid('id').defaultRandom().primaryKey(),
  name: text('name').notNull(),
  category: text('category'),
  unit: text('unit').notNull().default('kg'),
  retailPriceCop: numeric('retail_price_cop').notNull(),
  wholesalePriceCop: numeric('wholesale_price_cop'),
  wholesaleThreshold: numeric('wholesale_threshold'),
  active: boolean('active').notNull().default(true),
  updatedAt: timestamp('updated_at', { withTimezone: true }).defaultNow(),
})

export const conversations = pgTable('conversations', {
  id: uuid('id').defaultRandom().primaryKey(),
  channel: text('channel').notNull(),                 // messenger|whatsapp|instagram
  externalId: text('external_id').notNull(),
  customerName: text('customer_name'),
  status: text('status').notNull().default('bot_active'),
  lastMessageAt: timestamp('last_message_at', { withTimezone: true }).defaultNow(),
  createdAt: timestamp('created_at', { withTimezone: true }).defaultNow(),
}, (t) => ({ uniq: unique().on(t.channel, t.externalId) }))

// messages, leads, knowledge_gaps, bot_config, webhook_events, customer_profiles: análogas (ver §4 Entities)
```

**Habilitar pgvector** (primera migración): `CREATE EXTENSION IF NOT EXISTS vector;`

## 5. API Design

### Routes Overview
| Method | Path | Description | Auth |
|--------|------|-------------|------|
| GET | `/api/webhooks/meta` | Verificación del webhook (`hub.challenge`) | Público (verify_token) |
| POST | `/api/webhooks/meta` | Recibe eventos de los 3 canales | Público (firma HMAC) |
| POST | `/api/inngest` | Endpoint de jobs Inngest | Firma Inngest |
| POST/GET/DELETE | `/api/panel/knowledge` | Subir/listar/borrar fuentes | Admin (Clerk) |
| GET/POST/PATCH | `/api/panel/pricing` | CRUD de materiales/precios | Admin |
| GET/PATCH | `/api/panel/leads` | Listar/actualizar leads, aprobar descuento | Admin |
| GET/PATCH | `/api/panel/gaps` | Listar/resolver huecos de conocimiento | Admin |
| GET/PATCH | `/api/panel/conversations` | Ver hilos, tomar/liberar control | Admin |
| GET/PATCH | `/api/panel/config` | Leer/editar bot_config | Admin |

### Key Endpoints Detail

**`POST /api/webhooks/meta`** — el corazón del sistema
1. Verifica `X-Hub-Signature-256` con `META_APP_SECRET` (HMAC-SHA256). Si falla → 401.
2. **Responde 200 inmediatamente** (Meta exige < 20s; el procesamiento real va async vía Inngest o `waitUntil`).
3. Para cada evento:
   - Idempotencia: si `event_id` ya está en `webhook_events` → ignorar.
   - `normalize()` → `{ channel, externalId, customerName, text, messageId }`.
   - Si es un **echo** (mensaje enviado por un humano desde la bandeja de Meta) → marcar `conversation.status = human_controlled` y **no** responder. (Detección de relevo automático.)
   - Si `conversation.status === 'human_controlled'` → no responder (el humano lleva el hilo).
   - Cargar config + historial → ejecutar pipeline RAG (§ lib/ai) → enviar respuesta vía `send()`.
4. Forma de respuesta siempre `200 OK` a Meta (errores se loguean, no se propagan).

**`POST /api/panel/knowledge`** (multipart)
- Body: archivo (PDF/DOCX/PPTX/TXT) **o** `{ url }` para link **o** `{ text }` para texto plano.
- Sube a Vercel Blob → crea `knowledge_sources` (status `pending`) → dispara evento Inngest `ingest/source.uploaded`.
- Respuesta: `{ success: true, data: { sourceId, status } }`.

**`PATCH /api/panel/gaps`** (resolver hueco)
- Body: `{ id, answer }`.
- Marca el gap `resolved` → crea `knowledge_sources` tipo `faq` con `name = question` → embebe `Q: ... A: ...` como chunk → el bot ya puede responderlo.

**API Response Shape** (todas las rutas de panel)
```json
{ "success": true, "data": { } }
{ "success": false, "error": { "code": "VALIDATION", "message": "..." } }
```

## 6. Frontend Architecture

### Pages / Routes (panel)
| Route | Page | Description |
|-------|------|-------------|
| `/dashboard` | Dashboard | KPIs: conversaciones, leads nuevos, relevos pendientes, huecos abiertos |
| `/knowledge` | Conocimiento | Subir documentos/links/texto, ver estado de ingesta, borrar fuentes |
| `/pricing` | Precios | Tabla editable de materiales (minorista/mayorista/umbral) en COP |
| `/leads` | Leads | Solicitudes capturadas; aprobar descuentos personalizados; cambiar estado |
| `/gaps` | Huecos | Preguntas sin respuesta; resolver inline → enriquece la base |
| `/conversations` | Conversaciones | Hilos de los 3 canales; tomar/liberar control manual |
| `/settings` | Ajustes | Identidad/tono del bot, horarios, canales, privacidad/retención |

### Component Hierarchy (Knowledge page)
```
KnowledgePage (server)
  ├── UploadDropzone (client)        # arrastrar PDF/DOCX/PPTX/TXT o pegar link/texto
  ├── SourcesTable (server)
  │     └── SourceRow                 # estado: pending/processing/ready/failed + acción borrar
  └── IngestStatusPoller (client)     # refresca estado de fuentes en proceso
```

### State Management
- **Server Components por defecto**: las tablas (precios, leads, conversaciones) leen de la BD en el servidor.
- **Client Components** solo para interactividad: dropzone de subida, formularios, toggles de relevo, polling de estado de ingesta.
- Mutaciones vía **Server Actions** o rutas `/api/panel/*` con revalidación (`revalidatePath`).
- Sin estado global complejo: el panel es CRUD sobre la BD.

## 8. Authentication & Authorization

### Auth Flow
- **Panel**: Clerk. El admin inicia sesión en `panel.<dominio>/dashboard`. Sin registro abierto — solo el/los usuarios invitados en Clerk.
- **Webhooks de Meta**: NO usan Clerk (Meta no puede autenticarse). Se protegen con **verificación de firma HMAC** (`X-Hub-Signature-256`) + `verify_token` en el handshake GET.

### Protected Routes
- Protegido (Clerk middleware): todo `(panel)/*` y `/api/panel/*`.
- Público: `/api/webhooks/meta` (firma propia), `/api/inngest` (firma Inngest).

### Roles & Permissions
| Role | Can Do |
|------|--------|
| **admin** | Todo: conocimiento, precios, leads, descuentos, huecos, conversaciones, config |

(Rol único por ahora; el esquema permite añadir `agent` más adelante sin migración mayor.)

### Session Management
- Clerk gestiona sesiones (cookies httpOnly, refresh automático). No hay que construir JWT a mano.

- Configurar Clerk, `middleware.ts` que proteja `(panel)/*` y `/api/panel/*` y deje públicos los webhooks.
- Layout del panel con sidebar y guard. Verificar login funcionando.

**Step 4 — Capa de IA: embeddings + retrieval (RAG)**
- `lib/ai/embed.ts`: `text-embedding-3-small`.
- `lib/ai/retrieve.ts`: embeber la consulta → `ORDER BY embedding <=> $query LIMIT k` (cosine) → top-K chunks.
- Test: insertar un chunk manual y recuperar por similitud.

**Step 5 — Pipeline de ingesta (Inngest)**
- `lib/ingest/parse.ts` (PDF/DOCX/PPTX/TXT con librerías de parsing), `scrape.ts` (links), `chunk.ts` (troceado ~800 tokens, solapamiento 100).
- `inngest/functions/ingest-source.ts`: descarga del Blob → parse → chunk → embed → insertar chunks → `status = ready` (o `failed` con error).
- `app/api/inngest/route.ts`. Verificar end-to-end subiendo un PDF.

**Step 6 — Panel: Conocimiento**
- `app/(panel)/knowledge/*` + `api/panel/knowledge`. Subida a Vercel Blob, dispara Inngest, tabla con estado y polling. Borrar fuente (cascade a chunks).

**Step 7 — Panel: Precios**
- `app/(panel)/pricing` + `api/panel/pricing`. Tabla editable: nombre, unidad, precio minorista, mayorista, umbral, activo. Formato COP.

**Step 8 — Tools del bot (function calling)**
- `lib/ai/tools.ts`:
  - `lookup_price(material, quantity)` → consulta `materials`; aplica mayorista si `quantity >= wholesale_threshold`; devuelve precio o "no disponible".
  - `capture_lead({name, contact, interest, quantity, requested_discount})` → inserta `leads` + dispara `notify()` (WhatsApp al admin).
  - `request_human_handoff(reason)` → `conversation.status = human_controlled` + `notify()`.
  - `get_location()` → devuelve ubicación(es) desde el conocimiento.
  - `log_knowledge_gap(question)` → inserta `knowledge_gaps`.

**Step 9 — Motor de generación**
- `lib/ai/system-prompt.ts`: compone identidad + tono (desde `bot_config`) + reglas estrictas (solo responder con contexto; no inventar precios; capturar lead ante intención de compra; descuentos solo hasta `max_auto_discount_pct`, el resto deriva).
- `lib/ai/router.ts`: heurística mini → GPT-4o (longitud, palabras técnicas, fallo de RAG).
- `lib/ai/generate.ts`: arma mensajes (system + RAG + historial + tools) → llama OpenAI → ejecuta tools → respuesta final.

**Step 9B — Sistema de memoria (3 capas)**
- **Corto plazo** (✅ ya cubierto): cargar últimos N mensajes de `messages` por conversación.
- **Largo plazo** (cliente): al iniciar/continuar conversación, buscar `customer_profiles` por `(channel, external_id)`; si existe, **inyectar un resumen de `facts` en el system prompt** ("Cliente recurrente: interesado en cobre, suele comprar al por mayor"). Si no existe, crearlo. Vincular `conversations.customer_id`.
- **Actualización de `facts`**: job Inngest `memory/update-profile` que, al cerrar/inactivarse una conversación, extrae con el modelo los hechos nuevos (materiales, volúmenes, preferencias, nombre, empresa, contacto) y los fusiona en `customer_profiles.facts`.
- **Resúmenes**: cuando una conversación supera X mensajes, job Inngest `memory/summarize` que resume lo anterior en `conversations.summary`; el pipeline usa `summary + últimos mensajes` para acotar tokens.
- **Unificación entre canales** (opcional): si dos perfiles comparten `contact` (capturado vía lead), enlazarlos para continuidad de memoria.
- **Privacidad**: la memoria de cliente respeta `retention_months`; permitir borrado de perfil bajo solicitud (Ley 1581/2012).

**Step 10 — Integración Meta: webhook unificado**
- `lib/meta/verify.ts` (firma + verify_token), `normalize.ts` (Messenger/IG/WhatsApp → forma común), `send.ts` (Send API por canal + quick replies + tarjeta de ubicación), `notify.ts` (WhatsApp template al admin).
- `app/api/webhooks/meta/route.ts`: GET verify + POST (idempotencia, detección de echo/relevo, pipeline, respuesta < 20s con `waitUntil`).

**Step 11 — Panel: Leads + Conversaciones + Huecos**
- `leads`: tabla, aprobar descuento (`discount_approved_pct`), cambiar estado.
- `conversations`: lista por canal, hilo, **toggle tomar/liberar control** (cambia `status`).
- `gaps`: lista de abiertos, resolver inline → crea fuente `faq` y embebe (cierra el bucle de aprendizaje).

**Step 12 — Panel: Dashboard + Settings**
- Dashboard con KPIs. Settings: nombre/tono del bot, mensaje de bienvenida y fuera de horario, horarios, toggles de canal, número WhatsApp del admin, meses de retención, descuento máximo automático.

**Step 13 — Cumplimiento (Colombia / Habeas Data)**
- Página/política de privacidad y aviso de tratamiento de datos (Ley 1581/2012). Job de retención: borrar conversaciones más viejas que `retention_months`.

**Step 14 — Testing**
- Vitest: unit de `lookup_price` (mayorista/umbral), `chunk`, `normalize`. Integración de `/api/webhooks/meta` (firma, idempotencia, echo). E2E opcional (Playwright) del flujo de subida de conocimiento.

**Step 15 — Deploy (Vercel + Cloudflare)**
- Proyecto en Vercel, variables de entorno, Vercel Blob, registrar app de Inngest. Subdominio `panel.<dominio>` en Cloudflare (CNAME a Vercel). Health check.

**Step 16 — Conexión de canales Meta**
- Configurar webhooks en la Meta App (callback `https://panel.<dominio>/api/webhooks/meta`, `verify_token`), suscribir campos por canal, pegar tokens/IDs en env. Probar mensaje real en cada canal. (Requiere prerrequisitos de §17.)

## 16. Reglas No Negociables (para el builder)

1. **El bot solo responde con conocimiento verificado** (RAG) y precios desde `materials`. Cero alucinaciones.
2. **El webhook de Meta siempre devuelve 200 en < 20s.** Procesamiento pesado vía Inngest o `waitUntil`. Errores se loguean, no se propagan a Meta.
3. **Verificación de firma HMAC obligatoria** en el webhook + `verify_token` en el handshake GET.
4. **Idempotencia**: deduplicar por `event_id` (Meta reintenta). Detectar "echo" para el relevo humano.
5. **TypeScript strict, sin `any`.** Validación Zod en toda entrada. Respuestas de API con forma consistente.
6. **Descuentos controlados**: el bot solo ofrece hasta `max_auto_discount_pct`; lo demás se captura como lead y lo aprueba el admin.
7. **Privacidad (Colombia)**: aviso de tratamiento de datos (Ley 1581/2012) y retención configurable. Nunca commitear secretos.
